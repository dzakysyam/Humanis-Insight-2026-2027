# Rancangan integrasi website bidang, tahap lokal

Status: rancangan dan kontrak untuk implementasi bertahap. Bukan bukti OpenID Connect (OIDC), API V2, atau keputusan resmi telah aktif. Sumber kode yang diperiksa hanya `/workspace` Humanis.

## 1. Identitas: keadaan sekarang dan target

Saat ini `backend/src/interface/http/controllers/auth.controller.ts` menerima NIP/NISN dan kata sandi, lalu `AuthenticateSso` menerbitkan cookie `humanis_session` melalui HMAC issuer. `createServices` memasang `InMemoryIdentityRepository` dan revocation store in-memory. `OIDC_PENDING` hanya nilai katalog identitas. Cookie Humanis tidak otomatis berlaku di website bidang. Google Drive OAuth yang muncul pada UI bukan penyedia identitas bersama. Jangan menonaktifkan login lama sebelum migrasi teruji.

Target: tim IT memilih penyedia identitas OIDC dan memutuskan pemilik akun, identitas stabil `iss` + `sub`, klaim role, siklus akun, pemetaan NIP/NISN, serta URL staging. Humanis dan setiap website bidang menjadi client OIDC terpisah. Aplikasi bidang yang dibuka langsung menyimpan path tujuan secara server-side dalam state pendek berikat sesi browser, lalu memulai Authorization Code + PKCE ke penyedia identitas. Callback backend memverifikasi state, nonce, issuer, audience, signature/JWKS, expiry, redirect URI, dan menukar code lewat backchannel. Setelah valid, tiap aplikasi menerbitkan cookie sesi HttpOnly, Secure, SameSite yang sesuai untuk domainnya sendiri dan mengembalikan pengguna ke path internal yang tervalidasi. Bila sesi penyedia identitas masih ada, aplikasi kedua melewati prompt kata sandi. Token tidak lewat URL tujuan, tidak dipakai dari localStorage, dan backend tiap aplikasi memeriksa role serta scope record pada setiap request. Code callback OIDC memang parameter protokol sekali pakai; jangan menganggapnya access token atau mengirimkannya ke URL website bidang. Gunakan logout dan rotasi sesi yang disepakati. Simpan login lama sementara di belakang rencana cutover/rollback dan uji bersama tim IT.

## 2. Kepemilikan data dan kontrak laporan

Website bidang menyimpan draf, data operasional, versi, dan keputusan resmi. Humanis menyimpan metadata minimum serta status integrasi, bukan salinan bebas data siswa. Endpoint usulan `PUT /api/v1/integrations/reports/{sourceId}/{reportId}/versions/{version}` dipanggil backend bidang otomatis setelah pengajuan berhasil. Credential service-to-service di header lewat HTTPS (mTLS atau OAuth client credentials dengan audience dan scope khusus), tidak memakai cookie pengguna. Peta `sourceId` ke issuer/client dan izin scope di server. Batasi ukuran body, laju, sumber, dan jenis metrik; jangan menerima URL arbitrer sebagai tujuan callback.

Payload wajib: `sourceId`, `reportId` stabil di bidang, `period` (tipe dan awal/akhir atau ID periode yang disepakati), `version` integer positif, `previousVersion` bila revisi, `status` (misalnya SUBMITTED), `summary` berupa judul dan metrik yang diizinkan, `updatedAt` waktu dari sumber dengan zona waktu. Setiap metrik berisi key, definisi, unit, serta `value` angka atau `null`; `null` berarti tidak tersedia, bukan nol. Sertakan klasifikasi data dan tautan detail yang disetujui bila perlu; jangan kirim data pribadi tanpa persetujuan. Humanis mencatat `receivedAt` sendiri. `updatedAt` dan `receivedAt` berbeda; jika usia data melampaui SLA, tampilkan usang.

Kunci unik `(sourceId, reportId, version)` serta hash payload mencegah pengajuan sama terduplikasi. Kiriman identik aman diulang; konflik isi pada versi sama menghasilkan 409. Versi baru harus merujuk versi sebelumnya dan keputusan revisi. Gunakan outbox transaksional di bidang agar pengajuan yang berhasil tetap terkirim meski jaringan gagal. Humanis memproses secara idempoten. Status belum masuk/terlambat hanya dapat dihitung setelah jadwal laporan dan daftar sumber wajib disahkan; ketiadaan kiriman tidak berarti angka nol.

## 3. Keputusan Kepala Sekolah

Endpoint usulan browser `POST /api/v1/integrations/reports/{sourceId}/{reportId}/decisions` memerlukan sesi Humanis, CSRF, izin tindakan `REPORT_DECIDE` khusus Kepala Sekolah, scope sumber/record, `decisionId` idempoten, `expectedVersion`, aksi APPROVED, REJECTED, atau REVISION_REQUESTED, dan feedback tervalidasi. `MODULE_ACCESS` tidak cukup; Admin atau petugas TU tidak otomatis mendapat `REPORT_DECIDE`. Tolak sesi hilang, kedaluwarsa, role salah, dan versi/status tidak cocok sebelum meneruskan. Audit percobaan dan hasil tanpa credential atau data pribadi.

Humanis membuat intent keputusan PENDING secara durabel dan mengirim request terautentikasi ke API bidang terdaftar dari konfigurasi server: `decisionId`, `sourceId`, `reportId`, `expectedVersion`, aksi, feedback, dan identitas aktor terverifikasi. Backend bidang memeriksa credential service, kewenangan aktor sesuai delegasi yang disepakati, ID, versi, status SUBMITTED, serta constraint unik `decisionId`; update keputusan dan audit dalam satu transaksi dengan compare-and-swap. Bidang mengembalikan receipt berisi ID, versi, status resmi, dan waktu keputusan. Humanis mengubah status menjadi CONFIRMED hanya setelah receipt cocok atau hasil query rekonsiliasi ke bidang. Timeout atau respons ambigu tetap PENDING, tidak pernah sukses; retry memakai `decisionId` dan payload sama. ID sama dengan payload lain atau dua keputusan berlomba menghasilkan konflik. Perbedaan hasil ditandai NEEDS_RECONCILIATION, bukan ditutup otomatis. Versi revisi baru terhubung ke keputusan sebelumnya.

UI Kepala Sekolah membedakan PENDING, CONFIRMED, FAILED, dan NEEDS_RECONCILIATION. Label “Disetujui” hanya setelah CONFIRMED di bidang. Feedback tampil bersama sumber, periode, versi, status sinkronisasi, dan waktu pembaruan. Jangan memakai `humanisService.reviewSubmission` untuk laporan bidang: alur tersebut mengubah data demo in-memory Humanis tanpa konfirmasi pemilik data.

## 4. Tes lokal dan gerbang cutover

Gunakan layanan bidang palsu berlabel SIMULASI, data sintetis, dan identitas lokal; jangan menganggapnya API V2. Tes API positif/negatif: autentikasi service, payload invalid, duplikat identik dan konflik, role Kepala Sekolah/Admin/TU/Siswa, CSRF, sumber/record, feedback, versi usang, keputusan paralel, timeout sebelum dan setelah commit bidang, retry dengan ID sama, receipt tidak cocok, revisi, sesi kedaluwarsa, serta tidak tersedia vs nol. Tes Playwright: URL bidang langsung, kembali ke path semula, login sekali ke aplikasi kedua, penolakan backend, laporan masuk, keputusan confirmed/pending, dan status usang. Semua memerlukan provider OIDC lokal, Humanis, database, dan layanan bidang simultan. Rancangan ini belum memenuhi tes itu.

Sebelum implementasi produksi: tim IT harus menetapkan penyedia identitas, domain dan sertifikat, pemilik daftar role/izin, kontrak dan kredensial API bidang, periode wajib/SLA, ringkasan yang boleh dibagikan, retensi, backup/restore, migrasi data, serta rollback staging. Jangan push, deploy, atau menonaktifkan login lama dari tahap ini.
